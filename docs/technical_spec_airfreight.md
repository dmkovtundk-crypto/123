# Техническое задание
## Программный комплекс для автоматизации экспедиторской деятельности (авиаперевозки)

> Версия документа: 1.0 (базовая, консолидированная)
>  
> Дата: 2026-03-24

---

## 1. Введение

### 1.1 Назначение
Разработать веб-ориентированную информационную систему для управления полным циклом международных авиаперевозок: от получения заявки клиента до закрытия сделки и расчёта бонусов сотрудников.

### 1.2 Цели
- Централизованное управление сделками с привязкой документов, платежей и контрагентов.
- Прозрачность финансового результата по каждой сделке (план/факт, GP, маржинальность).
- Автоматизация согласований платежей и документов.
- Сокращение ручного ввода за счёт интеграций.
- Управление договорной базой.
- Мотивация сотрудников на базе фактической прибыли.

### 1.3 Пользователи
- Менеджер-логист
- Экономист
- Финансист
- Бухгалтер
- Руководитель
- Администратор

---

## 2. Архитектура

### 2.1 Рекомендуемый стек
- **Backend:** Python 3.11+, FastAPI
- **Frontend:** React + TypeScript, Redux Toolkit, Ant Design/Material UI
- **БД:** PostgreSQL 15+, Redis
- **Очереди:** Celery + Redis
- **Файлы:** S3-совместимое хранилище (MinIO/AWS S3)
- **API:** REST + OpenAPI (Swagger)
- **Контейнеризация:** Docker, docker-compose (локально), Kubernetes (опционально)
- **Мониторинг:** Sentry, Prometheus, Grafana

### 2.2 Архитектурный подход
Старт: модульный монолит с чёткими bounded contexts (DDD).
Перспектива: вынесение модулей платежей и интеграций в отдельные сервисы.

### 2.3 Принципы
- Полный аудит действий.
- Статусные модели для сделок и платежей.
- RBAC на уровне API.
- Привязка файлов ко всем ключевым сущностям.

## 3. Доменная модель (укрупнённо)

### 3.1 Основные сущности
- Contractor
- Contract
- Deal
- PlannedCost
- ActualCost
- PaymentRequest
- PaymentOrder
- BankStatement
- Document
- CustomsOperation
- ForwarderInstruction
- User
- BonusSheet

### 3.2 Ключевые связи
- Deal → Client (Contractor)
- Deal → Contract (опционально)
- PlannedCost/ActualCost → Deal
- PaymentRequest → Deal + Contractor + Contract
- PaymentOrder → PaymentRequest (опционально)
- BankStatement ↔ PaymentOrder (matching)
- Document → Deal/Contract/Contractor
- CustomsOperation → Deal

## 4. Роли и права (RBAC)

### 4.1 Менеджер-логист
- Ведение «своих» сделок.
- Черновая калькуляция.
- Создание заявок на оплату.
- Загрузка операционных документов.

### 4.2 Экономист
- Согласование калькуляций.
- План/факт-анализ и GP.
- Расчёт бонусов.

### 4.3 Финансист
- Согласование заявок на оплату (1-й уровень).
- Платёжный календарь, лимиты и резервы.

### 4.4 Бухгалтер
- Платёжные поручения и отправка в банк.
- Сопоставление выписок.
- Учёт первичных документов.

### 4.5 Руководитель
- Согласование низкомаржинальных сделок.
- Согласование крупных платежей.
- Утверждение бонусных ведомостей.

### 4.6 Администратор
- Пользователи, роли, справочники, системные настройки.

## 9. Безопасность
- JWT + refresh, опционально 2FA
- Хранение паролей: bcrypt
- RBAC + ограничение доступа менеджера к «своим» сделкам
- Audit log по изменениям
- Защита от XSS/CSRF/SQLi
- Доступ к файлам через signed URL

## 13. Критерии приёмки MVP
1. Пользователи с ролями могут входить и выполнять только разрешённые операции.
2. Сделка проходит все статусы до `closed` с журналом изменений.
3. Платёжная заявка проходит маршрут согласования по порогу суммы.
4. В карточке сделки доступны и версионируются ключевые документы.
5. По сделке доступен отчёт план/факт и расчёт GP.
6. Данные выгружаются в Excel минимум по списку сделок и платежному календарю.

---

## 14. Риски и допущения
- Форматы банков и ЭДО зависят от конкретного провайдера и требуют адаптеров.
- Интеграции с ФТС и AWB API могут потребовать отдельных юридических/договорных условий.
- Правила расчёта бонусов должны быть согласованы бизнесом до запуска в прод.
